## 1. Семантика path (из официального рантайма 4.3.13)

- **JSON-констрейнт** (`constraints[]` с `type: "path"`): `bones[]`, `slot` (имя слота, не кости!), `positionMode` `fixed|percent` (по умолчанию percent),
  `spacingMode` `length|fixed|percent|proportional` (по умолчанию length), `rotateMode` `tangent|chain|chainScale` (по умолчанию tangent), `rotation` (offset),
  `position`, `spacing`, `mixRotate` (1), `mixX` (1), `mixY` (= mixX), `skin`.
- **JSON-аттачмент**: `{type:"path", closed (false), constantSpeed (по умолчанию **true**), vertexCount, vertices (формат как у меша), lengths[], color}`;
  вершин в массиве `3 × число узлов` (для открытого пути крайние ручки — «пустышки»); `lengths` — длины кривых от начала (число кривых = узлы − 1, у замкнутого = узлы).
- **Таймлайны** (`animations.<n>.path.<constraint>`): `position`, `spacing` (по одному числу) и `mix` (`mixRotate`, `mixX`, `mixY`). Position-таймлайн аддитивный.
- **Алгоритм** `PathConstraint.update`: spaces по `spacingMode`, `computeWorldPositions` (две ветки: по `lengths` из файла при `constantSpeed=false`; по длинам,
  посчитанным в мировых координатах, при `constantSpeed=true`), затем для каждой кости `modifyWorld`: сдвиг к точке × mixX/mixY, масштаб (chainScale),
  поворот по касательной или цепочке. Поворот через `Math.atan2` и float32-π (`MathUtils.PI`).
- **Сортировка** (`PathConstraint.sort`): кости слота/пути всех path-аттачментов слота в активном и в дефолтном скине, затем кости констрейнта; после — `sortReset` детей,
  кости помечены `sorted = true` (он всегда меняет world).
- Вершины пути идут через `VertexAttachment.computeWorldVertices` — то есть **с деформацией слота** (`slot.deform`) и весами; значит ключи deform нужны и пути.

## 3. Заметки по ходу

**Блок A (path) — сделан.** Проверено: `tests/path.test.ts` (35: открытый / замкнутый / взвешенный путь, режимы, deform, alt-скин, мутанты, ручная геометрия),
`tests/pathedit.test.ts` (13: вставка / удаление узлов, привязка, deform-ключи, ключи констрейнта), fuzz.

- **Длины кривых (`lengths`) не хранятся**: считаются при компиляции скелета в позе настройки без констрейнтов (`fillPathLengths` в `skeleton.ts`, функция `pathCurveLengths`
  в `path.ts`, 64 шага на кривую). Экспорт пишет те же числа, поэтому наш солвер и официальный рантайм при `constantSpeed=false` видят одно и то же.
  `lengths` из импортируемого файла отбрасываются (пересчитываются) — на геометрию это не влияет, на распределение скорости при `constantSpeed=false` — в пределах точности замера.
- **Каждый компилированный скин владеет своей копией данных пути** (`lengths` зависят от позы этого документа, а кэш `compileAttachment` общий для документов).
- В JSON 4.3 `constantSpeed` по умолчанию **true** (загрузчик), а `mixY` по умолчанию = `mixX` — экспортёр пишет `mixY` всегда явно.
- **Особенность официального рантайма**: стартовая матрица кости — нули (у нас единичная). Path-констрейнт с путём, привязанным к костям (не к кости слота), читает матрицу
  кости слота ДО её обновления (только ради знака `offsetRotation`), поэтому в первом кадре свежего скелета официальный рантайм переворачивает знак смещения на один кадр.
  Со второго кадра оба видят матрицу прошлого кадра. Тесты сравнивают первые обновления свежих скелетов, поэтому наш скелет в них стартует с нулевыми матрицами
  (`startLikeOfficial` в `tests/official.ts`). Двойной `updateWorldTransform` вместо этого НЕ годится: официальный рантайм при повторном вызове накапливает действие слайдеров.
- Fuzz нашёл ровно это (8 из 300 сессий) — не баг солвера, а наследие стартового состояния; после `startLikeOfficial` все 8 проходят.
- **Второй прогон fuzz** (600 сессий, длинные) нашёл ещё 21 расхождение с официальным рантаймом; ни одно не оказалось ошибкой солвера. Что это было:
  1. **Кости цепочки в одной точке**: замкнутый путь и `spacing` = 4 длины пути (percent) → все `spaces` сворачиваются в одну точку, направление `atan2` берётся из
     шума ~1e-14 (у одного рантайма ровно 0, у другого 1e-14) — угол произволен. Такие констрейнты (`chain` / `chainScale`, соседние точки ближе 1e-3, `spaces[i+1] ≠ 0`)
     помечаются «неоднозначными».
  2. **Усиление шума**: позиция в `percent` умножается на длину пути, а на значения `position` / `spacing` слайдер приносит относительный шум ~1e-5 (float32-ключи у
     официального рантайма, 5 знаков экспортёра, на нашей стороне double); при позиции 27.6 длины пути (2760 %) это десятые доли единицы. Доказано опытом: если на
     момент `update` подставить в официальный констрейнт НАШИ `position / spacing / mix`, 5 из 7 сессий совпадают до 1e-4 (сид 143: 34.0598926 против 34.0598928).
  3. **Граница 0/360 слайдера** (уже известная неоднозначность) теперь доходит через path-констрейнт: слайдер анимирует кость слота пути, поэтому от неё зависят и
     сами кости констрейнта. Неоднозначность распространяется по констрейнтам (path → кости слота и весов пути, IK → цель, transform → источник, слайдер → драйвер).
  Для (2) и всех подобных цепочек в `tests/fuzzkit.ts` добавлен **оракул чувствительности**: расхождение между рантаймами прощается, только если сам официальный
  рантайм сдвигается на его десятую долю, когда все числа экспорта сдвигают на размер округления экспортёра (2e-5 + 2e-6·|x|). Ошибка не двигается от такого шума,
  поэтому остаётся видимой. Оракул работает для матриц костей, точек, вершин clipping / bbox / path.
- Deform пути хранится как у меша (дельты по точкам / по влиянию); вставка / удаление узла и перепривязка к костям **удаляют** deform-ключи этого пути (размер массива меняется).
- Не сделано в path: вставка узлов во взвешенный путь (тост), кнопки «сгладить / сделать угловым узел», веса пути кистью (только автопривязка).
